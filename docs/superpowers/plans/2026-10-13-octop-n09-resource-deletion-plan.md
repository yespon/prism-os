## 实施顺序和必须满足的行为

1. 固定个人/共享/pub 覆盖、无 actor、普通成员、跨租户/用户、重建同名、异常登记位置、别名/目录替换、缺文件及 Agent 引用的真实失败。确认 public 覆盖撤销与 public 原文件删除是不同操作，原 public 文件不能由租户 DELETE 回收。
2. 在任何文件或原生事实改动前核对当前权限、可选当前 resource_id、锁定原行及原登记目录。原记录不存在时 404 并保留目录/收据；已有未登记/无法证明归属发布内容不能按名字清理。旧未带条件客户端的兼容语义须明确，不能声称其证明跨请求同一实例。
3. 定义当前可核对的完整成员/目录身份、参考依赖和原操作边界。名称引用无法归属时明确拒绝物理回收，并提供后续引用解除/重新选择流程；该拒绝不是完整删除完成，也不能把禁用或留目录代替完整目标。共享资源必须按原当前租户权限检查关联范围。
4. 在原表和原收据服务上定义明确撤回/回收事实，不引入第二套资源注册表或执行事实。原配置移除与原生登记变更应使用同一 DB 事务、当前实例锁。原创建/恢复服务必须识别撤回，不能从旧收据无条件复活被撤回实例；同名新实例也不能被旧记录重新绑定。
5. 文件回收先证明归属，再通过安全描述符及同父目录排他移动隔离当前实例；确认移动的是已核对目录。目录替换、成员变化或未知状态须保留内容；仅可删除本操作已证明归属的隔离成员。发布、DB 提交、清理和响应不是跨存储事务，不自动猜测补偿。定义可持久检查的中断状态与恢复方式，避免残缺删除被 204 掩盖。实现中的收据扩展、状态机和动作须先与原 C1 兼容验证。
6. 用户明确确认当前具体资源，显示引用/冲突、未知检查及可核对恢复；当前身份、关闭/重开和晚响应隔离。删除完成、仅撤回、回收未完成必须分清，不能误导用户或重复派发。当前具体读取和当前使用授权共同核对被撤回资源，旧名字不能按同名 public 回退冒充原选中实例。
