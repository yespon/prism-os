# PrismOS 品牌根迁移设计

## 1. 决策摘要

PrismOS 是本项目唯一的产品品牌、工程身份和发布身份。现存 `OpsinTech` 命名不得继续作为别名、联合品牌、内部默认值或长期兼容接口存在。

本次迁移采用**有期限的兼容桥**：

- 新代码、新配置、新安装和新生成资源只使用 PrismOS 规范名称；
- 旧名称只允许作为旧部署的读取与迁移入口；
- 兼容逻辑集中在可独立删除的 legacy adapter 中，不进入核心业务模块；
- 兼容桥最多存活一个 minor 版本，并在紧随其后的 minor 版本删除；
- 历史资料可以保留旧名称，但必须明确标注为 `Legacy / Historical`；
- 用户数据不静默移动、不覆盖、不自动删除，迁移必须可预检、校验和回滚。

本设计取代《PrismOS 项目品牌与发布一致性迁移设计》中关于长期保留 `OPSINTECH_*` 和既有数据路径的兼容策略。该文档其余项目定位与发布原则继续有效。

## 2. 背景与问题

仓库和部分发布表面已经采用 PrismOS：

- GitHub 仓库为 `yespon/prism-os`；
- Python 项目名为 `prismos`；
- 前端包名为 `prismos-frontend`；
- Docker、GitHub Actions 和示例配置已有部分 PrismOS 默认值。

但旧品牌仍分布在多个层次：

- 前后端 README、API/架构/部署文档和脚本输出；
- 登录页、工作台、图片资源、提示信息和导出文件名；
- Agent 提示词、默认 Agent 名称、网站与仓库引用；
- 环境变量、数据目录、数据库默认位置和 Harness 配置；
- 浏览器 localStorage 键和前端事件名；
- 终端 marker、heredoc delimiter、User-Agent、存储桶和沙箱前缀；
- 默认管理员邮箱和其他新安装默认值。

这些残留并不都具有相同风险。公开文案可以直接纠正，配置和数据标识需要迁移，数据库结构与上游导入路径则不应因品牌清理被机械重命名。因此，本次工作不是全文替换，而是一次带兼容边界和数据安全约束的品牌根迁移。

## 3. 目标与非目标

### 3.1 目标

1. 让 PrismOS 成为产品、源码配置模型、部署资源和发布制品的唯一规范身份。
2. 清除所有用户、开发者和集成方可见表面中的旧品牌。
3. 将旧部署兼容收敛到单一、可观测、可删除的适配层。
4. 为旧数据目录和浏览器持久状态提供安全、可重复执行的迁移路径。
5. 建立 CI 品牌门禁，使旧名称只能减少，不能重新扩散。
6. 保持 Agent Runtime、数据库、API 和既有用户数据的行为兼容。

### 3.2 非目标

本次迁移不包含：

- 重命名 `deerflow` Python 包或导入路径；
- 重写 Alembic 历史、数据库表名、已有 API 路由或持久化主键；
- 重构 DeerFlow/LangGraph 运行时；
- 实现白皮书中的 Workflow、Policy、Evaluation 等新平台能力；
- 删除未完成迁移的用户数据；
- 把 AgentOS 建立为与 PrismOS 并列的第二品牌。

## 4. 唯一命名规范

| 层级 | 规范名称 |
|---|---|
| 产品与 UI 品牌 | `PrismOS` |
| GitHub 仓库 | `yespon/prism-os` |
| 本地仓库目录 | `prism-os` |
| Python 项目/发行包 | `prismos` |
| 前端包 | `prismos-frontend` |
| 环境变量 | `PRISMOS_*` |
| 用户数据目录 | `.prismos` |
| 浏览器存储键 | `prismos_*` |
| 前端事件名 | `prismos:*` |
| Docker 服务、容器和网络 | `prismos-*` |
| OCI 镜像 | `ghcr.io/yespon/prism-os` |
| 对象存储桶和前缀 | `prismos-*` |
| User-Agent | `PrismOS/<version>` |
| 默认本地域名和邮箱 | `prismos.local` |
| 品牌资源文件 | `prismos.svg`、`prismos-full.svg` |

边界规则：

- `AgentOS` 只表示产品类别、架构理念和白皮书系统范式，不作为代码包、服务或仓库的第二品牌。
- `DeerFlow`、`LangGraph` 等名称只表示上游依赖或内部技术边界。公开材料可以准确描述依赖关系，但不能让依赖名称替代 PrismOS 产品身份。
- `OpsinTech` 不再作为默认值、别名或联合品牌。除 legacy adapter、迁移工具、测试夹具和明确标注的历史资料外，任何新增命中均视为缺陷。
- 本地目录最终从 `prism-platform` 调整为 `prism-os`，不重写 Git 历史。

## 5. 旧名称分类与处置规则

每个旧名称命中必须归入以下一种类别，并按对应规则处理：

| 类别 | 典型位置 | 处置 |
|---|---|---|
| 公开品牌面 | README、UI、提示词、文档、脚本输出、资源名 | 本轮直接改为 PrismOS，不保留别名 |
| 新安装默认值 | 环境示例、数据目录、邮箱、User-Agent、bucket、sandbox | 本轮改为 PrismOS，新安装不得创建旧名资源 |
| 旧部署输入 | `OPSINTECH_*` | 仅由 legacy adapter 读取，兼容一个 minor |
| 持久客户端状态 | localStorage 键、前端事件 | 读旧迁新、只写新；验证成功后清理可安全删除的旧键 |
| 用户数据位置 | `.opsintech` | 自动发现、显式迁移、复制校验、保留旧目录回滚 |
| 内部协议标识 | marker、EOF delimiter | 确认无外部依赖后改名，并以协议回归测试保护 |
| 历史事实 | 历史设计、Release Notes、迁移说明 | 可保留，但必须标注 `Legacy / Historical` 并加入白名单 |
| 运行时兼容边界 | `deerflow` import、表名、迁移 ID、API 路由 | 保留；不属于旧品牌清理范围 |

禁止通过全仓机械替换处理数据库、迁移、协议和数据路径。每类命中必须由其所属迁移单元负责。

## 6. 兼容与迁移架构

### 6.1 总体边界

```text
旧部署输入 ──→ Legacy Adapter ──→ PrismOS 规范配置 ──→ 核心系统
OPSINTECH_*       读取、告警、转换       PRISMOS_*          只认识新名
.opsintech
旧浏览器键
```

Legacy Adapter 是旧名称唯一可进入运行时的入口。核心业务、Gateway、Harness、Sandbox 和 Storage 只消费规范化后的 PrismOS 配置对象，不得直接读取旧环境变量或旧路径。

若上游组件暂时只能消费旧变量，转换必须位于单一上游边界适配器内，并有测试证明不存在向其他模块扩散。不得用全局反向导出旧环境变量维持兼容。

### 6.2 环境变量

对每一组新旧变量执行以下确定性规则：

1. 存在 `PRISMOS_*` 时使用新变量；
2. 新旧变量同时存在且值不同，以新变量为准并输出冲突警告；
3. 只有 `OPSINTECH_*` 时允许兼容启动，输出弃用警告及对应新变量名；
4. 新变量存在但无效时直接报告新配置错误，不静默回退旧变量；
5. 日志只显示变量名和配置来源，不显示密钥、令牌或连接字符串的值；
6. 启动诊断可以将来源标记为 `PrismOS`、`Legacy` 或 `Default`。

新文档、Compose、示例配置、CI 和部署脚本只公开 `PRISMOS_*`。

### 6.3 用户数据目录

新安装只使用 `.prismos`。启动检查只发现 `.opsintech` 时，应给出迁移命令和兼容截止信息，但不得静默移动数据。

迁移命令采用以下流程：

```text
dry-run/预检 → 记录源状态 → 复制到临时目录 → 完整性校验
                                                ↓
                                      原子切换为 .prismos
                                                ↓
                                      保留 .opsintech 供回滚
```

预检至少覆盖：

- 源目录存在性与权限；
- 目标目录冲突；
- 可用磁盘空间；
- 符号链接和特殊文件；
- 当前运行进程或文件锁风险；
- 关键数据库和配置文件的可读性。

迁移必须满足：

- 支持 `--dry-run`；
- 不覆盖既有非空目标目录；
- 失败时不切换活动目录；
- 对本次创建的临时产物执行安全清理；
- 生成机器可读清单和人工可读摘要；
- 记录文件数量、总大小和关键文件校验结果；
- 重复执行得到稳定结果；
- 不自动删除旧目录。

回滚只改变活动目录选择或配置，不删除 `.prismos` 或 `.opsintech`。用户确认迁移成功后，才可通过显式清理命令处理旧目录。

### 6.4 浏览器持久状态

每个受影响的 localStorage 键采用“新键优先、旧键迁移、只写新键”的策略：

1. 读取 `prismos_*`；
2. 新键不存在时读取对应旧键；
3. 旧值解析和校验成功后写入新键；
4. 再次读取新键验证成功后，删除可安全删除的旧键；
5. 解析失败时保留旧值并记录非敏感告警，不阻断应用启动；
6. 后续写入只允许使用新键。

旧前端事件名只在确有跨版本页面或插件通信需求时由过渡适配器监听。新代码只发布 `prismos:*` 事件。

### 6.5 数据库、API 与对象存储

- 数据库文件的新默认名称和位置采用 PrismOS 规范，但不重命名表、迁移历史或已有数据中的稳定标识。
- API 对外展示文本和新生成的非稳定标识采用 PrismOS；既有路由不因品牌迁移改变。
- 新对象存储 bucket/prefix 采用 `prismos-*`。
- 对既有旧 bucket 不做隐式复制或删除；提供检测、权限验证和迁移指引。真实对象迁移需要独立确认，因为它可能产生存储与流量成本。

### 6.6 内部协议标识

`__OPSINTECH_MARKER_*`、`OPSINTECH_EOF` 等标识在确认仅用于进程内部通信后改为 PrismOS。确认工作包括：

- 搜索生产代码、脚本、插件、文档和测试中的生产者/消费者；
- 验证标识不会持久化到任务记录或外部系统；
- 增加 marker 解析、命令边界和异常输出的回归测试。

如果发现外部消费者或持久化实例，旧标识暂时进入协议适配器，并遵守同一 minor 兼容期限。

## 7. 组件改造范围

### 7.1 产品与公开表面

本轮覆盖：

- 根目录、前后端 README；
- API、架构、安装、部署和开发文档；
- 登录页、工作台、落地页、通知和错误信息；
- Agent 系统提示词、默认名称、示例网站和仓库引用；
- CLI 帮助、Shell 输出、日志标题和导出文件名；
- Logo、图片路径、HTML metadata 和页面标题；
- 默认管理员邮箱、User-Agent、bucket、sandbox 和其他产品默认值；
- GitHub About、Topics、Issue/PR 模板、Release 模板和 Packages 元数据。

旧图片资源先创建 PrismOS 命名资源并切换引用；确认生产代码和构建产物无引用后再删除旧文件。

### 7.2 配置规范化层

建立单一 PrismOS settings 模型和独立 legacy input adapter。所有直接读取 `OPSINTECH_*` 的业务代码迁移到规范 settings；兼容告警、冲突规则和移除版本只在适配层定义。

### 7.3 数据与客户端迁移单元

迁移能力拆分为可独立测试的单元：

- 数据目录发现与迁移器；
- 浏览器存储键迁移器；
- 前端事件过渡适配器；
- 对象存储旧资源检测器；
- 迁移清单、校验摘要和回滚说明生成器。

### 7.4 上游依赖边界

保留 `deerflow` 导入路径及相关运行时适配目录。删除上游模板中遗留的旧产品网站、仓库、默认 Agent 名称和虚构引用。公开材料统一表述 PrismOS 与 DeerFlow/LangGraph 的实际依赖关系。

### 7.5 仓库与发布外壳

代码与迁移入口稳定后，从父目录将本地仓库目录调整为 `prism-os`，并同步开发文档、CI/CD、镜像、Compose project、容器、网络、volume、安装脚本和 Release 文案。

目录调整不修改 Git 历史，也不改变远端 `yespon/prism-os`。执行前必须确认没有脚本、IDE 配置或自动化任务硬编码旧绝对路径。

## 8. 兼容期限与删除条件

兼容桥在**首次包含本迁移的 minor 版本**中提供，并在**紧随其后的 minor 版本**删除。示例：若迁移首次发布于 `0.2.x`，则 `0.3.0` 删除运行时兼容读取。它不得跨越两个 minor 版本。

首次迁移版本必须：

- 在启动日志和迁移文档中声明移除版本；
- 对每次 legacy 输入使用产生可观察的弃用事件；
- 记录兼容入口的测试覆盖和白名单；
- 发布显式迁移命令与回滚说明。

紧随其后的 minor 版本必须：

- 删除运行时旧环境变量、旧路径和旧浏览器事件的兼容读取；
- 删除 legacy adapter 和对应运行时白名单；
- 保留独立离线数据迁移工具，使未及时升级的数据不会被困死；
- 将 CI 运行时代码旧名允许数量降为零。

## 9. 失败处理与回滚

### 9.1 数据迁移失败

- 目标已存在：默认中止，不覆盖；
- 空间不足或权限错误：预检失败，不开始复制；
- 复制中断或校验失败：不切换活动目录，保留原数据；
- 临时目录清理失败：报告精确路径，由用户确认后处理；
- 回滚：切回旧数据源或原配置，不删除任一数据副本。

所有删除操作必须与迁移成功解耦，且需要用户显式执行。

### 9.2 配置失败

- 新配置无效时报告新配置错误；
- 旧配置无效时报告 legacy 输入错误和新配置替代方式；
- 新旧冲突不阻断启动，但必须可观察；
- 任何诊断都不得输出敏感值。

### 9.3 客户端状态失败

损坏或无法解析的旧浏览器状态不应阻断页面启动。系统保留原键、使用安全默认值，并记录可诊断但不含业务数据的错误信息。

## 10. 品牌门禁

CI 增加旧名称扫描。门禁不采用无法解释的全仓目录豁免，而使用逐项白名单。每个允许项至少包含：

- 精确文件路径；
- 命中用途；
- 分类：兼容代码、迁移工具、测试夹具或历史资料；
- 移除版本；
- 责任模块。

规则如下：

1. 新增未列入白名单的旧名称命中，CI 直接失败；
2. 白名单不得使用仓库根目录或宽泛 glob；
3. 历史文档必须包含 `Legacy / Historical` 标识；
4. 兼容代码白名单总数设置不可增长上限；
5. 删除旧命名时同步收缩白名单；
6. 紧随迁移版本后的 minor 版本，运行时代码白名单归零；
7. `deerflow` 等获准保留的上游技术身份不属于旧品牌命中。

扫描范围包括受版本控制的源码、文档、配置、脚本和资源文件名。构建缓存、虚拟环境、`node_modules`、工作树、`.superpowers/` 和用户运行数据不进入扫描输入。

## 11. 验证策略

### 11.1 品牌表面测试

- README、UI、提示词、CLI、文档和默认值无未获准旧品牌；
- 页面标题、图片路径、导出文件名和构建产物使用 PrismOS；
- 仓库 URL、镜像地址、安装命令与实际发布身份一致。

### 11.2 配置契约测试

- 新变量优先；
- 仅旧变量时兼容读取并告警；
- 新旧冲突时新值胜出；
- 无效新值不回退；
- 日志不泄漏敏感值；
- 核心模块不直接读取旧变量。

### 11.3 数据迁移测试

- 无旧目录；
- 正常迁移；
- 目标冲突；
- 空间和权限失败；
- 复制中断；
- 校验失败；
- 重复执行；
- 回滚；
- 符号链接与特殊文件；
- 旧目录始终不会被隐式删除。

### 11.4 前端状态测试

- 新键优先；
- 旧键成功迁移；
- 后续只写新键；
- 损坏数据不会阻断启动；
- 可安全清理的旧键只在新键验证后删除。

### 11.5 协议与部署测试

- terminal marker、EOF delimiter、Sandbox 和 Harness 行为保持一致；
- Compose、镜像、容器、网络、volume 和健康检查使用 PrismOS 名称；
- 旧部署在兼容版本可启动并获得迁移提示；
- 新安装不创建旧命名资源。

### 11.6 回归测试

现有后端、前端、数据库迁移和端到端检查必须证明本次工作未改变 Agent 执行、API 契约和白皮书 roadmap 的平台能力边界。

## 12. 实施顺序

实施按以下依赖顺序进行：

1. 建立品牌词汇表、命中清单和 CI 门禁基线；
2. 清理公开品牌面和新安装默认值；
3. 建立 PrismOS settings 与 legacy adapter，迁移业务模块读取点；
4. 实现数据目录和浏览器状态迁移；
5. 核验并迁移内部协议标识；
6. 收拢上游边界和部署资源命名；
7. 调整本地仓库目录与发布外壳；
8. 运行全量验证，收缩白名单并发布迁移说明；
9. 在紧随其后的 minor 版本删除运行时兼容桥。

该顺序保证先建立判定标准，再改变运行时输入，最后调整工作区外壳，降低并行修改导致的漏项和回归风险。

## 13. 完成标准

本轮品牌根迁移只有同时满足以下条件才算完成：

- PrismOS 是产品、配置模型、部署资源和发布制品的唯一规范身份；
- 核心业务代码不存在对 `OPSINTECH_*` 或 `.opsintech` 的直接依赖；
- 所有旧部署输入只经过隔离的 legacy adapter；
- 新安装不创建任何旧命名资源；
- 数据迁移可预检、校验、重复执行和回滚；
- 所有公开表面通过品牌扫描；
- 白名单逐项可解释，兼容项只能减少；
- 兼容桥明确绑定首次迁移版本及紧随其后的删除版本；
- 本地目录调整为 `prism-os`，远端保持 `yespon/prism-os`；
- 数据库表、迁移历史、API 路由和 `deerflow` 导入兼容未受破坏；
- `.superpowers/`、本地数据库、用户数据和构建缓存不进入提交。

完成本规格不等于完成白皮书能力建设。品牌根迁移是 M1/P0 平台实施的前置治理工作；完成后，项目继续以已批准的 PrismOS 能力 roadmap 为主线推进，AI 运维仍只作为验证场景，不与系统内核耦合。
