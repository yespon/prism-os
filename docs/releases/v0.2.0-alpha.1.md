# PrismOS v0.2.0-alpha.1

**Status:** Pre-release / alpha
**Release tag:** `v0.2.0-alpha.1`
**Compatibility family:** `0.2.x`
**Runtime compatibility removal:** `0.3.0`
**Repository:** <https://github.com/yespon/prism-os>
**Image:** `ghcr.io/yespon/prism-os:v0.2.0-alpha.1`
**Python package:** `prismos==0.2.0a1`
**Frontend package:** `prismos-frontend@0.2.0-alpha.1`

PrismOS is a governed Agent operating system foundation for enterprise teams.
This release establishes the single PrismOS product identity across runtime
configuration, browser state, deployment resources, packages, and release
artifacts. It is the only minor-version compatibility bridge for the brand
migration: operators may use the compatibility inputs described below during
the `0.2.x` family, but runtime reads of those inputs are removed in `0.3.0`.

## What changed

- PrismOS is the canonical public product, repository, package, and image identity.
- New environment variables, data homes, browser keys, and deployment resources
  use the `PRISMOS_*`, `.prismos`, `prismos_*`/`prismos:*`, and `prismos-*`
  namespaces respectively.
- The runtime adapter gives canonical `PRISMOS_*` values precedence. Invalid
  explicit canonical values do not fall back to legacy values.
- The browser migration reads a legacy value once, verifies the canonical copy,
  removes the legacy key only after successful verification, and writes only the
  canonical key thereafter.
- The home migration is explicit, dry-run by default, hash-verifies every file,
  activates atomically, preserves the source, and supports rollback.
- Legacy remote object-storage resources are detected and planned only. This
  release never copies or deletes real remote objects automatically.
- CI now blocks Docker build and container publish workflows when an unclassified
  legacy brand token appears in tracked content.

## Migration

Run the preflight without changing the filesystem:

```bash
export PRISMOS_LEGACY_SOURCE="/path/to/preserved-source-home"
uv run python scripts/migrate_prismos_home.py \
  --source "$PRISMOS_LEGACY_SOURCE" \
  --target ~/.prismos
```

Review the plan, take an independent backup, then explicitly apply it:

```bash
uv run python scripts/migrate_prismos_home.py \
  --source "$PRISMOS_LEGACY_SOURCE" \
  --target ~/.prismos \
  --apply
```

The apply path copies to a temporary target, verifies file size and SHA-256 for
every file, writes a migration manifest, and atomically activates the target.
It does not silently move, overwrite, or delete the source. Stop the service
before switching homes.

### Rollback

The preserved source remains the rollback authority. Set the canonical home to
that source and restart the service:

```bash
export PRISMOS_HOME="$PRISMOS_LEGACY_SOURCE"
```

If the migrated target has already received new writes, restore from the backup
or reconcile those writes before attempting another migration. Do not delete
either home as part of rollback.

### Environment compatibility

During `0.2.x`, the host-boundary adapter may read the legacy deployment inputs
listed in the migration guide and normalize them to `PRISMOS_*`. The canonical
input always wins. New deployments must use canonical names immediately. The
legacy aliases and automatic runtime discovery are removed in `0.3.0`.

### Browser state

On first access, PrismOS reads a valid legacy browser value, writes and verifies
the corresponding canonical key, then removes the legacy key. Malformed legacy
values are retained for recovery and do not become canonical state. New writes
use only the canonical PrismOS namespace.

### Object storage

The release detects legacy object-storage resources and produces a plan for
operator review. It does not copy, rename, or delete remote objects. Operators
must perform any provider-specific data movement separately, with their own
backup, permissions review, and rollback plan.

## Breaking changes

- Runtime compatibility inputs are temporary and have a hard removal boundary at
  `0.3.0`; this bridge will not be extended into a second minor version.
- New installations must use `PRISMOS_HOME` and `.prismos`. Deployments that
  rely on legacy aliases must complete migration before upgrading to `0.3.0`.
- New browser state is written under PrismOS keys. Consumers that directly read
  private legacy keys instead of using the storage helpers must migrate.
- Published coordinates are now `prismos`, `prismos-frontend`, and
  `ghcr.io/yespon/prism-os`.

Existing database schemas, API paths, persistence identifiers, Alembic history,
LangGraph graph/checkpointer interfaces, and `deerflow` imports are intentionally
unchanged.

## Known limitations

- This is an alpha foundation release; the full AgentOS whitepaper roadmap is
  not claimed to be implemented by this release.
- The migration CLI requires sufficient free disk space and refuses open files,
  symbolic links, existing targets, and unsupported special files.
- Object-storage migration remains operator-managed; no remote copy or delete is
  performed by PrismOS.
- The compatibility bridge is intentionally observable and finite. Teams should
  remove legacy inputs before the `0.3.0` upgrade rather than depend on silent
  fallback behavior.
