# PrismOS v0.1.0-alpha.1

> **Legacy / Historical:** This document records an earlier project state and may contain superseded product names or compatibility decisions.

**Status:** Pre-release / alpha  
**Release tag:** `v0.1.0-alpha.1`  
**Release baseline:** `8d117cf6a87ae4f33fa627487dd55f1873b4f91a`  
**Repository:** <https://github.com/yespon/prism-os>

PrismOS is a governed Agent operating system foundation for enterprise teams.
This first alpha establishes the product identity, compatibility boundary,
public documentation, CI validation, and the first container publication path.
It is a foundation release, not a claim that every capability in the whitepaper
has already been implemented.

## What is included

The current implementation provides the following platform capabilities:

- multi-tenant user and resource scopes;
- platform and tenant RBAC with protected management routes;
- database-backed model/provider configuration and tenant assignment;
- scoped Skill management, import, editing, and sandbox testing;
- tenant-scoped MCP configuration and health checks;
- local, Docker, and optional Kubernetes sandbox adapters;
- thread files, uploads, generated artifacts, preview, and download;
- user, tenant, announcement, audit-view, and administration surfaces; and
- optional vertical plugin surfaces for alerting, terminal, and assets.

Agent management, plugin SPI, runtime abstraction, and a unified audit model
exist only as partial foundations. The next roadmap layers are Policy,
Task/Run lifecycle, Workflow, Evaluation and observability, Connector
federation, runtime independence, and cross-organization Federation. These are
not complete PrismOS contracts in this alpha.

AI operations is a validation scenario, not a PrismOS architectural dependency.
The core platform is intentionally kept useful for other enterprise Agent
scenarios.

## Runtime and architecture boundary

The full local application is assembled by the repository's Docker Compose
stack: nginx, the Next.js frontend, the FastAPI gateway, LangGraph, database
initialization, and an optional Kubernetes sandbox provisioner. Start that
stack with:

```bash
make config
make up
curl http://localhost:2026/health
```

The current execution foundation remains the DeerFlow-compatible harness and
LangGraph. The `deerflow` Python import boundary, existing API routes, database
tables and migrations, and historical data paths remain intentionally
unchanged for compatibility.

## Container publication

The release workflow publishes the following multi-architecture GHCR image:

```text
ghcr.io/yespon/prism-os:v0.1.0-alpha.1
```

Supported target platforms are `linux/amd64` and `linux/arm64`. The image
contains the PrismOS backend and Agent runtime built from `backend/Dockerfile`.
It is not a self-contained all-in-one image for the full web application; the
repository Compose stack remains the canonical complete deployment path in
this alpha. The release workflow writes version, commit, source, and revision
OCI metadata and does not publish a `latest` tag.

Use the immutable version tag after confirming the package visibility and
workflow result in the GitHub repository:

```bash
docker pull ghcr.io/yespon/prism-os:v0.1.0-alpha.1
```

The GHCR package is expected to follow the repository's private visibility
policy. A pull may therefore require GitHub authentication and package access.

## Configuration compatibility

New deployments use the following precedence:

```text
PRISMOS_* → OPSINTECH_* (legacy input) → PrismOS defaults
```

The default new runtime directory is `backend/.prismos`. If it does not exist
and `backend/.opsintech` exists, the resolver can use the existing directory in
place without copying, renaming, deleting, or rewriting it. Back up existing
data before changing an explicit path. Do not commit populated configuration,
credentials, API keys, or database passwords.

## Security and alpha limitations

This release is not a security certification, production isolation guarantee,
or backward-compatibility promise. In particular:

- the default local filesystem sandbox executes on the host;
- Docker-socket modes can provide substantial host control;
- Kubernetes provisioner mode requires operator-managed RBAC, quotas, image
  provenance, network policy, and kubeconfig protection;
- MCP servers, model providers, Skills, plugins, and generated artifacts are
  external trust boundaries; and
- PrismOS does not yet provide a complete centrally enforced Policy engine,
  Task/Run or Workflow lifecycle, Evaluation framework, Connector federation,
  or independent Agent runtime.

Review [SECURITY.md](../../SECURITY.md) before enabling untrusted code,
third-party MCP servers, Docker/Kubernetes sandboxing, or external model
providers.

## Verification status for this release baseline

The release baseline was checked with:

```text
git diff --check                         PASS
bash -n scripts/*.sh                      PASS
docker compose config --quiet             PASS
docker compose -f docker/docker-compose.yaml config --quiet  PASS
docker compose -f docker/docker-compose-dev.yaml config --quiet PASS
bash scripts/test-prismos-env.sh         PASS
backend pytest --collect-only -q          1173 tests collected
```

The complete backend suite is not a passing release gate. The previously
recorded baseline was `973 passed, 18 skipped, 184 failed`; the failures are
primarily existing DeerFlowClient contract drift and other unrelated behavior
gaps, not pytest collection failures. This alpha must not be represented as a
fully passing backend release.

Frontend static checks were not runnable in the local worktree because
`frontend/node_modules` was absent (`eslint: command not found`). The GitHub
workflow installs dependencies before running `pnpm check`. Docker images were
not built locally; the multi-architecture build and GHCR publication require
an actual GitHub Actions run.

## Upgrade and feedback

Treat this release as an installation and architecture-validation baseline.
Keep a backup of runtime data and database volumes before upgrading. Use the
repository's private security channel for vulnerabilities, and consult
[CONTRIBUTING.md](../../CONTRIBUTING.md) for focused changes and validation
expectations.

The next implementation sequence follows the whitepaper foundation roadmap:
Governance primitives → Task/Run execution lifecycle → Workflow lifecycle →
Evaluation and observability → Connector/runtime independence → Federation.
