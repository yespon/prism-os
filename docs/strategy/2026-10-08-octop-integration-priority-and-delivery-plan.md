# Octop 全量集成：优先级与实施节奏调整建议

**日期：** 2026-10-08（Asia/Shanghai）
**状态：** 响应“可批量搬运 Octop 源码”的排期修订建议；不覆盖原 Approved 文档，不表示源码迁入或里程碑已经完成。
**目标：** 当前 PrismOS 能力 + Octop 当前公开能力完整等价 + PrismOS 原设计与规划能力；Octop 尚未发布的后续方向另建增量交付清单。
**本地基线：** HEAD `d7ef525`；正在另行开发的未提交 SecretRef 管理接口不计作完成。
**上游迁入候选基线：** Octop `v1.0.2b6`，固定提交 `eb28011249c02cafd389b2d424294c6c1b9cf422`；最新 main 调研基线和未来路线继续使用 [全量复核](./2026-10-08-octop-full-capability-roadmap-review.md) 的固定提交。

## 1. 应调整的是交付顺序，保留的是设计、不变量和最终能力

建议把此前“M1 → M2 → M3 → M4 → M5 → M6 → M7，然后配套 Octop 产品”的串行交付，改为 **产品闭环驱动的纵向交付 + 同步完成平台契约与验收**。上游已经存在的知识、定时任务、专家共享和协作功能，不应仅因原来被映射到 M5/M6/M7，就等到 2028 年才开始提供。

原 [Capability Roadmap](../superpowers/specs/2026-08-08-prismos-capability-roadmap-design.md) 的能力、退出门、兼容要求和 C1/C2 条件投资保留。原日历、完整阶段的串行关系与新增产品包的启动方式需要形成明确的增量排期修订；不能同时宣称“原排期完全不变”和“提前交付完整 Octop 能力”。本建议尚未改写原批准文件。

提前交付不等于跳过依赖：调度单 Agent 需要持久 Run、Occurrence 去重和受控动作，但不必等待完整 Workflow DAG；知识问答需要 Secret、文档 ACL、索引撤权与来源，但不必等待通用 Connector 平台全部完成；专家复用需要固定配置快照和使用权限，但不必先完成全部 Deployment 与包市场。**把这些必要切片提前补齐，完整 M4–M7 的能力与正式验收仍逐项收口。**

旧复核的 O01–O42、F01–F12、D1–D8 编号继续使用。旧文档的阶段落点说明原依赖；本建议给出新的候选交付顺序，不把旧串行日历作为新增产品的唯一上线时间。

## 2. 当前基础决定的第一优先级

当前并非从零开始：已有 Tenant/Membership/RBAC、Skill/MCP、文件与 Artifact、模型 Provider、Terminal、Local/Docker/Kubernetes Sandbox、多服务部署以及部分 IM；`backend/app/runtime_adapters.py` 已提供宿主配置、持久化与执行校验接缝。这些应成为承接 Octop 的基础，不能在迁入时丢失现有 Slack、Kubernetes 或 AIOps 能力。

`d7ef525` 已提交严格加密、持久工单 SecretRef 和存储密钥轮换。仍待完成管理员接口、Provider 最小注入、旧明文配置迁移，以及新迁移的 PostgreSQL/目标部署和真实模型/webhook 验证。依据 [当前 SecretRef 设计与实施记录](../superpowers/specs/2026-10-08-m1-ticket-secret-ref-design.md) 和 [M1 门禁记录](./2026-09-25-m1-exit-gate-evidence.md)，M1 尚未退出，试点开关仍默认关闭。

因此 P0 是**收口已经开始的 M1，而非重写 SecretRef**；同时可做上游清单、内容迁入准备与兼容性试验。新的通用 Secret 接缝需要单独冻结 owner/purpose/scope 契约，不能把仅限 `ticket.create`、Source 绑定的工单仓库直接当作任意 Connector 密钥库。

| 优先级 | 先交付的价值 | 同期必须补齐的 PrismOS 能力 | 不等待的“大阶段” |
| --- | --- | --- | --- |
| P0 | 既有 AIOps 治理闭环；证明一个 Octop 功能可接入现有宿主 | 完成 M1 收口；固定上游、依赖与迁移边界 | 不先换 Runtime、不先整套搬数据库 |
| P1 | 专家/人格/共享资源、统一工作台与可追踪执行 | 同一身份；最小持久 Task/Run/Attempt/Action；固定执行配置与 Policy/资源引用；Runtime 调用接缝 | 全量 M4 资产运营、完整 M7 市场 |
| P2 | 私有知识问答、带引用研究、两个参考 Connector | 通用 Secret 最小契约、租户文档/索引 ACL、撤权、来源与同步状态；AIOps + 企业研究双场景评价 | 全量 M6 目录与所有数据后端 |
| P3 | 定时任务、主动推送、多渠道与 AgentTeams | 单任务调度与投递幂等、父子 Run、预算/取消/恢复、审批后的真实执行检查 | 完整 M5 DAG、通用分布式调度 |
| P4 | ACP、浏览器/终端、远程桌面/手机、多模态和桥接 | 每类动作 PEP、设备所有权与撤销、Artifact/成本、受控远程 Adapter | 全量客户端打包、云边自动调度、C1/C2 |
| P5 | 资产/Workflow/扩展完整生命周期；剩余目录、身份、多端与运维对齐 | M2–M7 原退出项完整收口；包权限/签名/兼容/回滚；专项运行证据 | 不用“已复制目录”冒充全量完成 |

人格模板、专家库等低成本内容可以在 P0/P1 批量迁入准备，但排期优先级仍低于可用执行、知识和自动化闭环；只有审批、凭据或设备控制的界面不能算功能上线。

## 3. 如何批量搬运源码，才会真正提速

### 3.1 三类迁入策略

| 类别 | 候选范围 | 处理方式 |
| --- | --- | --- |
| A：成批迁入，改动少 | 专家/子 Agent/MBTI 内容、内置 Skill 资料、非执行性目录、解析与格式转换的纯逻辑、i18n 文案、可复用 fixture | 保留许可证、来源提交和清单；先查隐含 shell/联网/凭据依赖。迁入数量与实际可运行数量分开记录 |
| B：成批迁入模块，逐接缝适配 | Knowledge、Connector、Cron、Team、Browser/ACP/设备、多模态、前端页面、CLI 与渠道 | 保留算法和用户流程；替换身份、Repository、执行、Secret、Storage/Artifact 和 API 接缝；以完整用户路径为迁入单位 |
| C：复用能力，宿主实现继续由 PrismOS 承担 | OctopServer 启动、JWT/用户库、原 SQL 迁移、线程/执行事实、全局管理鉴权、默认桌面自带服务升级器、任意插件的主进程加载 | 不覆盖 PrismOS 现有内核；必要时复用协议/纯逻辑，功能接到原宿主。功能没有被删除，只是其系统责任不直接照搬 |

主仓之外还依赖 `octop-harness`、`octop-memory`、`octop-gateway`、`octop-browser`。只复制 Octop 主仓无法取得完整行为。R0 要生成依赖版本与来源清单，实际解出锁定组合；不能把上游版本范围或 `octop-harness[all]` 直接加入现有环境并视为兼容。出现 LangGraph/SDK 冲突时，优先缩小依赖或隔离为能力 Worker；替换 DeerFlow/LangGraph 仍受 C1 约束。

建议代码布局为独立、可比对的迁入能力包与宿主 Adapter，例如 `backend/packages/octop-capabilities/` 和 `backend/app/integrations/octop/`。这是候选布局，须在 R0 试验后定稿，不是本次已创建的包。原平台契约继续放在已有 `app.platform`；原 Alembic 链保持单一 head。不得保留两套用户、租户、数据库迁移或业务执行事实源。

### 3.2 接缝的实际成本

已经抽查的固定 b6 源码显示：`api/deps.py` 的身份来自 OctopServer/JWT；Knowledge 的 owner/shared 归属与宿主服务绑定；CronManager 使用进程内 APScheduler/Repository/Gateway；Team 服务依赖 RepoBundle 和作业追踪。它们不是把 import 路径改名就能完成 PrismOS 纳管的独立模块。

| 接缝 | 必须解决的事项 | 迁入后的责任归属 |
| --- | --- | --- |
| 身份与资源 | Octop user/owner/shared 映射到 tenant/actor/scope；分享、复制、编辑、撤回分开授权 | PrismOS Identity/Resource/Policy |
| 数据和文件 | Repository、异步事务、ID、对象存储、索引与后台任务上下文；同租户过滤贯穿缓存与 Worker | PrismOS 数据模型/迁移/Storage |
| 执行与恢复 | Cron、IM、Team、ACP 都创建/关联 Run；父子取消、超时、断线与 unknown 提交有确定语义 | PrismOS Task/Run/Attempt/Action；Runtime 仅负责执行与 checkpoint |
| 凭据与副作用 | SecretRef 绑定/撤销/最小注入；每个实际工具动作经 Policy/Approval/Audit；shell 等替代路径不能绕门 | PrismOS Secret Provider 与执行 PEP |
| 客户端与协议 | 同一会话/租户、API 错误、SSE/WS、附件、审批与重连；兼容既有入口 | PrismOS Gateway/API 与公共客户端契约 |

### 3.3 前端与桌面应采用的加速方式

Octop Dashboard 是 React 18/Vite/Ant Design；PrismOS 当前是 Next 16/React 19。建议短期保留**独立构建的能力工作台**，由同一域名下的路由承载，接 PrismOS 会话与 API facade、统一导航和租户切换。先迁入完整业务页面，逐步统一视觉与关键页面；不要求第一批把所有页面重写成 Next。独立构建可以避免立即合并 React 依赖，但 session/CSP、资源 base、路由及 WebSocket 仍需实际验证。不能再提供一套 Octop 登录、管理员和模型账户。

桌面客户端与远程桌面是两个能力。Octop Wails 壳默认会启动自身便携 Octop 后端；直接搬默认启动逻辑会引入第二宿主。先复用壳的远程服务连接方式，提供连接 PrismOS Gateway 的客户端；完整离线/便携安装再编排现有多服务内核。R4 可先验一个目标平台，R6 补齐 Windows/macOS/Linux、对应架构与 NAS 制品；原生构建、升级/备份/回退不能从壳源码存在推定已通过。

## 4. 建议实施节奏

### 4.1 4–5 名持续投入成员的容量假设

以下是**待 R0 实测修正的工程规划区间**，不是基于迁入率测量得到的发布日期。团队需具备后端治理、能力集成、前端/客户端和部署验证能力；外部供应商、原生构建环境与凭据需可获得。开发窗口按主依赖串行相加约 20–30 周，另留 4–6 周跨端、目录与上线整合容量，形成 24–36 周候选全量窗口。独立内容、客户端与部分连接器可并行，但不要再次把乐观并行收益重复计入。

| 交付轮次 | 建议窗口 | 主要交付与 O 编号 | 进入下一轮的具体证据 |
| --- | --- | --- | --- |
| R0：收口与迁入试验 | 1–2 周 | M1 剩余任务；上游/依赖/许可证清单；一个端到端迁入试验；冻结最小执行与接缝方案 | 同一租户/身份通过 PrismOS 执行迁入能力；拒绝/撤权/故障有效；M1 剩余证据明确；测出一个模块真实迁入成本 |
| R1：专家与统一执行 | 2–3 周 | O01/O02/O04–O08/O10/O11/O15/O21/O26：专家/人格/共享资源、基础工作台、Web/CLI、文件与模型；最小持久 Run 和执行快照 | 原聊天/AIOps/Slack/K8s 路径可用；刷新与重启执行事实不丢；旧 API/配置兼容；共享不共享凭据或私有会话 |
| R2：知识与连接器 | 2–3 周 | O19/O20/O23–O25：记忆/知识产品、引用研究、Secret 接缝与两个参考 Connector；其他目录逐步迁入 | AIOps 与企业研究共用平台；删文档/撤权后不能召回；凭据不进入 API/Prompt/Audit；刷新/限流失败可恢复 |
| R3：自动化与团队 | 3–4 周 | O09/O12–O14：IM、Cron/date/run-now、主动推送、AgentTeams；剩余通道列出验收任务 | 重启/重复触发无重复副作用；投递重试不重执行业务；团队父子 Run 可追踪并有真实取消/审批/预算语义 |
| R4：工具、设备和多模态 | 4–6 周 | O16–O18/O27–O33/O41：本地模型、语音/图像/视频、ACP、Browser/Terminal/Desktop/Phone、录制与桥接；单平台远程客户端试用 | 每类操作权限落实到执行；断线/撤权可停止；录制仅产生受控草稿；外部执行 unknown 不盲重试；费用/输出可归因 |
| R5：平台完整生命周期 | 4–6 周 | O36–O39/O42：可信插件与目录、质量/可观测、产品助手；完整 AgentVersion/Deployment、最小 Workflow、评价晋级、扩展权限/签名/回滚 | 原 M2–M5 退出项收口；M6 数据与 Connector 项有完整证据；M7 至少三类真实独立扩展、SDK/包生命周期可验证 |
| R6：全量对齐与交付收口 | 4–6 周 | O03/O22/O34/O35/O40：SSO/LDAP、数据后端、多平台客户端/PWA/NAS、运维；全目录/通道/子能力差距清零 | 每个当前公开子能力都有等价用户路径和运行证据；原平台余项通过；升级、恢复、目标数据库和各平台制品验收 |

轮次表示主交付焦点，不表示该组所有子能力只在该轮开发或必然完成。R1 的共享包不等于 M7 完成，R3 的 Team/单任务调度不等于完整 Workflow；R5 也不能用“平台退出”替代剩余连接器、客户端和运维的功能对齐。SSO 若为试用准入要求应前移 R1/R2；低成本可信插件、只读管理助手、质量回归和 PWA 应提前随功能交付。

对 O35，本轮全量窗口覆盖已公开 PWA，原生移动内测作为 F05 另列；对 O37，覆盖已公开目录发现/安装，完整公共生态作为 F11 另列；对 O42，覆盖已发布产品助手，管理所有资源作为 F12 另列。R6 不是对尚未开放的上游代码作搬运承诺。

**推荐对外目标：** 约 6–10 周交付首个专家 + 私有知识 + 可追踪任务的试用闭环；约 8–12 周形成自动化/团队的主要使用闭环；当前公开能力完整等价的候选窗口 24–36 周，R0 后按实际成本重新估算。试用可以是明确受限的功能切片，不代表 M1–M7 或 O01–O42 全部通过。

### 4.2 如果维持原来 1–2 人

原路线以 1–2 名持续开发者为主，不能把上表的 4–5 人窗口直接套用。建议仍按 R0→R1→R2→R3 交付价值，先做 **8–12 周试用窗口** 的容量核算，首版只承诺专家、受控执行和选定知识/连接器路径。全量能力继续保留在验收清单，R0 后用测得的模块工时、目录数和实际人数估算剩余时间，不在未测迁入率时许诺一个全量发布日期。

人力较少时，一次只推进一个完整功能接缝；不能为了同时开设备、多客户端和全部 IM 而让 M1 凭据、执行事实与权限检查长期悬空。增加成员首先补集成/前端和发布验证，而非建立第二个 Runtime 团队。

### 4.3 每两周的工作机制

- 一个迭代必须演示至少一条用户闭环；最大同时推进两条能力迁入，各有唯一 Owner。纯搬文件不算交付。
- 建议常态容量约 60% 产品迁入、25% 必要平台契约与治理、15% 集成/迁移/发布验证。P0 按实际缺口倾斜；这些是容量安排，不代表安全门只有 25% 覆盖。
- 每条闭环包含来源版本、成功/拒绝/恢复/故障证据、数据迁移与回退方案，并记录上游测试改写后的实际通过范围。避免复制只验证旧宿主的测试后报全绿。
- 每四周复核一次能力差距和上游增量。固定候选版本不在日常开发中自动追 main；经兼容、回归与迁移验证后再升级，不把追随上游变更作为额外交付主线。
- 四到五人时建议责任覆盖：平台/DB/治理、上游能力迁入、前端/客户端、集成/部署验证；第五人承接第二条模块迁入。所有领域共同遵守同一契约与发布门。

## 5. 原 PrismOS 规划如何保留并完善

| 原规划 | 提前做的必要切片 | 最终仍必须完成的能力 |
| --- | --- | --- |
| M1 治理 | P0 完成工单；新工具发布时立即接动作 PEP | 确定性 allow/deny/require_approval、审批/撤权、关键审计故障拒绝副作用；不宣称工单试点覆盖所有工具 |
| M2 执行生命周期 | R1 Run 事实与快照；R3 子 Run、Occurrence、投递关联 | 完整状态、Attempt/Action/Event、有限重试、取消、超时、恢复、幂等和 unknown/orphaned 处置 |
| M3 Runtime 与质量 | R1 调用接缝；R2 双场景和最小评价门 | start/stream/pause/resume/cancel/get_state、消息/工具/checkpoint/error 映射、Dataset/EvaluationRun/Score/Gate；Runtime 中立 |
| M4 资产 | R1 固定配置/权限与引用，不继续依赖运行时可变配置 | AgentDefinition/Version/Deployment、正式发布/停用/回滚、版本与评价关联；不能把快照冒充完整资产平台 |
| M5 Workflow | R3 单任务调度与父子编排 | 版本化 Agent/Tool/Approval/Condition 最小 DAG、等待/恢复、Event/Schedule；每次触发只产生受治理执行 |
| M6 数据与 Secret | R2 中立 Secret 接缝、Knowledge ACL、两类 Connector | Document/Chunk/IndexVersion/来源、Secret/OAuth 生命周期与撤销、标准错误/限流/同步；所有目标目录与后端另验 |
| M7 扩展 | 可信包白名单、来源 digest、最小 manifest 与权限声明随首版做 | SDK/CLI、签名/权限、隔离、兼容、升级回滚、企业目录；三类真实扩展的独立边界；公共分发另验 |
| C1/C2 条件投资 | R4 受控 ACP/Remote Adapter 与 Bridge 等价 | 只有出现原定义的硬证据才投资自研 Runtime 或 Federation；桥接/云边功能不自动触发 |

完善原设计的重点是执行时冻结实际配置、将版本/数据/Secret 引用与权限传到底层动作，并让后台 Worker、设备操作与远程调用参与同一治理闭环。不是只在新前端外面加 RBAC。

所有功能发布仍需满足其切片的硬门。原完整阶段的启动条件、证据、真实重复需求、Owner/容量以及停止/迁移条件继续用于完整平台立项和验收；这次建议需要显式允许已经具备依赖的有限产品切片先行，不能用先行切片宣布上一完整阶段已经退出。

## 6. Octop 后续方向的优先级

“当前完整能力”和“未来方向全部规划”保留为两张清单。不能将尚未公开的原生移动、自进化、托管或云边调度代码计入批量搬运收益，也不能因上游未开放就从目标清单删除。

| 官方路线编号 | 本建议优先级与节奏 | 与原 PrismOS 的关系 |
| --- | --- | --- |
| F01/F02 共享池/共享专家 | R1 做产品路径，R5 收口版本和分发生命周期 | 与 M4/M7 一致，必要切片提前 |
| F03 PC 客户端 | R4 首个平台远程壳，R6 全平台与便携/升级路径 | 体验层增量，不新建 Runtime |
| F04 AgentTeams | R3 Beta 等价并加治理，R5 深化资产/Workflow | 与协作目标一致，自主 Team 与确定性 DAG 分别验收 |
| F05 原生移动内测 | R1 起冻结公共 API/审批/重连；当前 PWA 先交付；拿到源码或决定自研后再单独估时 | 新客户端产品；不能用 Remote Phone/PWA 代替 |
| F06 Browser/Terminal 补全 | R4；只读/浏览能力可更早，写操作按动作接门 | 复用既有工具/Sandbox，不扩成通用 RPA |
| F07 自进化 | R4 录制/对话产生 Skill 草稿；R5 后评测→审阅→发布→回滚 | M3/M4/M7 提供基础，生产自动晋级需额外证据；不得自动提权 |
| F09 Project | R2/R3 先组织现有会话/文件/任务的聚合视图；稳定资源/成员 ACL 后形成正式 Project | 白皮书 Workspace 的自然补足，无需等托管业务 |
| F12 对话式控制面 | 首批只读产品助手；按资源逐个增加受治理写 API | 随已纳管 API 增长；不允许模型直写数据库 |
| F11 公共插件市场 | R5 私有供应链和当前目录；之后独立做公共发现/审核/升级与运营 | 公共生态超出原默认范围，但完整目标保留；不凭私有目录宣称完成 |
| F08 Managed Agents | 当前产品与部署可靠性收口后，独立托管工作包 | 新增容量/隔离/运维产品，开通与 Deployment CRUD 不同 |
| F10 云边端一体 | R4 先实现受控桥接；之后做路由、驻留、预算、失联与未知提交 | 远程使用可提前，自动调度另立项；跨独立组织再评估 C2 |

上述是 PrismOS 的建议，Octop 官方 README 没有为这些方向提供可据以排期的统一交付日期。R0 后先估当前发布能力；未来包在代码可得性、真实需求、人员和专项验收明确后各自估时，不与 24–36 周当前全量窗口混算。

## 7. 第一个两周应交付什么

1. 收口已经开始的工单 SecretRef 管理、Provider 注入和明文迁移，完成部署证据；M1 的剩余门逐项判断，不用新功能挤掉收口工作。
2. 固定 b6 来源与全部外部能力包，建立模块/目录/许可证清单；保留 MIT 通知，单独核对外部依赖和素材来源，不只记录主仓许可证。
3. 用“一个专家通过 PrismOS 会话完成一条带文件/检索的任务”做迁入试验，检查数据库、Runtime、前端与撤权的真实接缝；再对一个代表模块试做两个选定上游版本之间的增量更新，记录冲突、适配变化与兼容证据。必须记录不可直接复用的代码比例、首次迁入与后续更新工时；试验工作量超出窗口时据实修订 R0。
4. 冻结最小 Run/执行快照、中立 Secret 和宿主 Adapter 增量设计，以及临时工作台/API 契约；据试验修正 R1–R6 工时。必要的架构修订落入实施 Spec 后再开发核心表/API。
5. 将 O01–O42 子能力、F01–F12 增量、PrismOS 原能力组成发布账本：来源、目标轮次、Owner、实现、测试/真实部署证据、迁移/回退和缺口。目录自动生成条目后逐项验收，不用“已接入两个 Connector”替代全部目录。

完整完成的定义仍是：当前公开能力的每条用户路径有等价实现和运行证据，现有 PrismOS 能力不回退，原平台最终能力和硬门通过；未来新增方向各自闭环。不能用源码迁入率、API 路由数量或页面数量替代这些结果。

## 9. 能否支撑 Octop 后续规划持续融入

### 9.1 判断与当前证据边界

**可以作为持续融入的架构方向，但目前只能判定“具有可建设的接缝”，不能判定“已经验证可持续升级”。** 方案已有固定来源、独立能力包、宿主 Adapter 与统一治理方向；还需要将上游差异维护、契约版本、依赖组合及第二版本增量验证变成正式交付物。一次迁入跑通不证明这些条件成立。

本轮重新读取 [Octop main 官方路线](https://github.com/TencentCloud/Octop/blob/main/README.md#-roadmap)，仍列出 AgentTeams Beta、原生移动内测，以及自进化、Managed Agents、Project、云边端、市场和对话式控制面规划；官方仍说明路线可调整。未来接口、实现语言和模块边界没有稳定兼容承诺，不能为尚未发布的代码保证无冲突搬运。

Octop [固定 b6 架构](https://github.com/TencentCloud/Octop/blob/eb28011249c02cafd389b2d424294c6c1b9cf422/docs/architecture.md) 使用 OctopServer 组合宿主、进程内管理器和用户行级归属。PrismOS 的 `runtime_adapters.py` 已有配置/持久化/执行校验等宿主回调，但不是覆盖未来功能的通用 Octop 接口。这支持继续提取模块边界的建议，也解释了后续不会是零成本更新。

### 9.2 首次迁入必须增加的持续维护机制

| 机制 | 首次迁入就要留下的交付物 | 对后续融入的作用 |
| --- | --- | --- |
| 完整上游基线 | 可恢复的固定源码镜像/基线；每个迁入文件映射来源路径、commit、许可证、依赖包版本和本地负责人 | 后续可从旧上游到新上游比较，不靠搜索本地改名后的文件猜来源；镜像仅作追溯，不运行第二套宿主 |
| 独立差异记录 | 上游原样基线、必要补丁与 PrismOS Adapter 分开；说明补丁原因、影响接口、可撤销条件 | 保留三方合并依据；避免租户/Secret/Run 逻辑散落后每次升级重做。业务模块无法完全不改时保留小而明确的补丁，不假设全部可用 wrapper 解决 |
| 契约与能力声明 | 接口版本、可用能力、请求/事件/错误 schema；映射 tenant/actor/资源/Run/Artifact/Secret；每模块可启停 | 新能力显式协商；缺失能力和未知动作拒绝或清楚标为不支持，不默认继承管理权限；契约变更经过迁移与兼容设计 |
| 可解的依赖组合 | 主仓及外部能力包的锁定组合；同进程/独立 Worker 的支持矩阵和跨进程协议版本 | 不把单个库升级等同整套可用；出现依赖冲突时有边界可隔离，仍保留一套业务执行事实与治理 |
| 双层验证 | 模块行为/协议回归 + PrismOS 契约/治理/旧功能回归；至少一个代表模块的第二版本增量演练 | 前者检验上游能力有没有丢，后者检验租户、撤权、Secret、审批、恢复和现有能力有没有被破坏；改变宿主后不能照搬全部上游测试结论 |
| 版本与数据升级路径 | 升级清单、幂等数据迁移、混合版本是否允许、停止/回退方式、备份恢复证据 | 回退不能只退源码。已写入新 schema 的数据必须可兼容读取、受控恢复或明确禁止旧版启动，不能假定数据库无损降级 |

运行依赖方向应是：PrismOS 组合宿主提供 Adapter，迁入能力通过约定接口使用身份、存储、执行和凭据；上游原样镜像不承载产品授权。禁止在原样镜像内直接散布 `app.platform` 导入；确有必要的宿主解耦改动进入独立补丁或提取包。保留内部来源路径有助于差异比较，不必为了产品品牌全局替换每个源码名称。

### 9.3 不同未来方向的融入路径

以下是建议的工程判断，不是 Octop 对可复用率或交付时间的承诺。

| 未来变化 | 持续融入方式 | 需提前建设的接缝 |
| --- | --- | --- |
| 专家/Skill/连接器目录、人格、解析、普通工具增强 | 对固定来源做增量同步，再验内容/协议/权限；耦合模块仍需适配 | 来源 manifest、版本引用、工具 schema、包权限 |
| AgentTeams 与 Browser/Terminal 增强 | 保留上游调度/交互逻辑；新派工、工具和事件映射到父子 Run/Action；检查新增副作用 | 执行能力声明、取消/预算、事件投影、设备会话与动作 PEP |
| 原生移动与桌面增强 | 客户端对接稳定公共 API；协议变化独立版本化，设备 SDK/打包另验 | 会话/租户切换、审批、重连、Artifact；与宿主启动和升级解耦 |
| Project | 复用可能发布的业务流程/UI；将资源关系与成员映射到 PrismOS 权限和数据模型 | 稳定资源引用、成员 ACL、项目关联和生命周期；先冻结边界，不提前造空表 |
| 自进化 | 复用提取/生成逻辑；候选进入 PrismOS 评价、审阅、版本发布与回滚 | 来源/授权、草稿、Evaluation、Agent/Skill Version、晋级门；不能复制自动提权或绕过评价的发布路径 |
| Managed Agents / 云边端 | 可复用协议或 Provider 客户端；Provision/Placement/Quota/Residency 等基础设施语义单独设计 | Runtime/Deployment Provider、远程身份、预算、驻留、租约和 unknown 提交；不由桥接自动满足 |
| 公共市场 / 对话式控制面 | 分发/发现接现有包生命周期；对话产生管理 Action 并调用正式 API | 包兼容/签名/权限/隔离/撤销；管理 API 的 Policy/Approval/Audit |

新增方向即使需要扩展平台契约，也可以与既有迁入模块共存；这就是原 PrismOS Runtime 中立、版本、质量与供应链规划的价值。若未来上游换掉核心宿主或引入不兼容数据模型，应重新评估该模块的边界，允许选择移植行为或独立能力服务，不能承诺继续原样复制整个应用。

### 9.4 持续升级的工作流与成本判断

每轮升级采用：**上游旧/新版本差异盘点 → 接口/依赖/数据/副作用分类 → 能力包与补丁整合 → 两层回归和迁移验证 → 隔离租户验证 → 分批发布与回退检查**。上游 PR 合并和 README 更新只进入候选清单，不自动进入生产，也不证明其源码已可取得。主仓与四个外部能力包分别跟踪，再验证支持的版本组合。

延续每两周交付、每四周上游复核的节奏；这描述团队工作方式，本次没有创建定时监控。持续整合必须在既有迭代容量内预留 Owner 和工时，不能以零成本附加到此前产品排期上。维护容量根据第二版本试验修正，新功能吞吐和 24–36 周候选窗口也随实测更新。

发布账本增加：已吸收上游版本、待吸收变更及原因、补丁数量/影响范围、依赖兼容结果、首次与增量整合工时、原能力回归、数据迁移/回退证据。若连续版本都要求修改 PrismOS 核心、补丁增长无法收敛、协议语义不能正确映射或依赖组合无法维护，则暂停该模块自动跟进，重新拆分接口或改为功能等价实现；目标能力仍保留。

**R0 的持续性验收：** 除首次功能运行外，至少对一个代表模块完成第二上游版本的候选更新，能解释全部来源差异和本地补丁，证明没有新增第二身份/执行事实源，新增动作权限通过，旧功能与数据兼容通过，并记录实际工时。不满足时仍只能叫首次迁入方案，不能宣称已具备持续吸收上游的能力；一个模块通过也不能证明所有模块通过。
